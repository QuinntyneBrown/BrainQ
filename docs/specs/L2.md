# L2 - Detailed Requirements

## L2-001: Entity Schema
**Traces to:** L1-001, L1-008

The system shall persist a single `Entity` table with columns: `Id` (UUID), `Type` (enum/string: Person, Project, Commitment, Note, Idea), `Title` (string, required), `Body` (text, nullable), `Subtitle` (string, nullable), `Tags` (text[]), `Attributes` (JSONB for type-specific fields), `Embedding` (vector(1536), nullable), `CreatedUtc`, `UpdatedUtc`.

**Acceptance Criteria:**
1. Given a fresh database, when migrations run, then the `Entity` table exists with all listed columns and a GIN index on `Attributes` and an HNSW (or IVFFlat) index on `Embedding`.
2. Given an `Entity` insert with an unknown `Type` value, when the request is processed, then it is rejected with a 400 response naming the invalid type.
3. Given an `Entity` insert with `Title` longer than 200 characters, when the request is processed, then it is rejected with a 400 response.

---

## L2-002: Edge Schema
**Traces to:** L1-001, L1-003

The system shall persist a single `Edge` table with columns: `Id` (UUID), `FromEntityId`, `ToEntityId`, `Type` (enum/string: mentions, blocks, fulfills, relatesTo), `CreatedUtc`. The pair (`FromEntityId`, `ToEntityId`, `Type`) shall be unique.

**Acceptance Criteria:**
1. Given two existing entities, when an edge is created between them with a valid type, then the edge persists and is returned by subsequent queries.
2. Given an attempt to create a duplicate edge with the same from/to/type, when the request is processed, then it is rejected with a 409 response.
3. Given an edge referencing a non-existent entity, when the request is processed, then it is rejected with a 400 response.
4. Given an entity is deleted, when its deletion is committed, then all edges referencing it are removed in the same transaction.

---

## L2-003: Entity CRUD API
**Traces to:** L1-002

The system shall expose REST endpoints: `POST /api/entities`, `GET /api/entities/{id}`, `GET /api/entities?type=&q=`, `PUT /api/entities/{id}`, `DELETE /api/entities/{id}`.

The Capture screen is the only currently designed write surface; edit and delete affordances on the Detail screen are **UI design pending** and gated by a future design pass.

**Acceptance Criteria:**
1. Given a valid entity payload, when `POST /api/entities` is called, then a 201 response is returned with the new entity including server-assigned `Id`, `CreatedUtc`, and `UpdatedUtc`.
2. Given an entity exists, when `GET /api/entities/{id}` is called, then the entity is returned with 200.
3. Given a `PUT` request with partial data, when processed, then unspecified fields retain their prior values and `UpdatedUtc` is refreshed.
4. Given a `DELETE` request on an entity with edges, when processed, then the entity and its edges are removed atomically and a 204 is returned.

---

## L2-004: Edge CRUD API
**Traces to:** L1-003

The system shall expose: `POST /api/edges`, `GET /api/edges?fromId=&toId=&type=`, `DELETE /api/edges/{id}`. Edges are immutable apart from creation and deletion.

Edge creation is currently surfaced only as suggested links during capture (see L2-011); explicit edge-creation and edge-deletion UI are **UI design pending**.

**Acceptance Criteria:**
1. Given a valid edge payload, when `POST /api/edges` is called, then a 201 response returns the persisted edge.
2. Given query parameters, when `GET /api/edges` is called, then matching edges are returned.
3. Given an edge id, when `DELETE /api/edges/{id}` is called, then the edge is removed and 204 returned.

---

## L2-005: Structured Query
**Traces to:** L1-004

The `GET /api/entities` endpoint shall accept query parameters: `type` (single or comma-separated), `q` (case-insensitive substring match against `Title`, `Body`, and `Tags`), `relatedTo` (entity id; returns entities linked by any edge), `edgeType` (constrains `relatedTo`), `from`/`to` (ISO 8601 date range against `CreatedUtc`), `take` (default 50, max 200), `skip`.

The Brain screen exposes `type` and `q`; `relatedTo`, `edgeType`, and date filters are accessible only via API in the current design (UI surfacing them is pending).

**Acceptance Criteria:**
1. Given 100 entities of mixed types, when `GET /api/entities?type=Person` is called, then only Person entities are returned.
2. Given an entity A linked to B via `mentions`, when `GET /api/entities?relatedTo={A.id}&edgeType=mentions` is called, then B is returned.
3. Given `take=10` and 50 matches, when called, then exactly 10 results are returned with a way to page (e.g., `skip`).
4. Given `take=500`, when called, then the response is capped at 200 results.

---

## L2-006: Embedding Generation
**Traces to:** L1-005

On entity create or when `Title`/`Body` change, the system shall compute an embedding from the concatenated `Title` and `Body` and store it in the `Embedding` column. Embedding generation shall happen synchronously within the request unless the text exceeds a configured threshold, in which case a background task may complete it.

**Acceptance Criteria:**
1. Given a new entity with text content, when created, then `Embedding` is non-null on the persisted record.
2. Given an entity update that changes `Title` or `Body`, when persisted, then `Embedding` is recomputed.
3. Given an entity update that changes neither `Title` nor `Body`, when persisted, then `Embedding` is unchanged.
4. Given the embedding provider is unavailable, when an entity is created, then the entity persists with `Embedding=null` and a warning is logged; the entity remains discoverable via structured query.

---

## L2-007: Semantic Search Endpoint
**Traces to:** L1-005

The system shall expose `GET /api/search?q=&type=&take=` that converts `q` to an embedding and returns entities ranked by cosine distance.

**Acceptance Criteria:**
1. Given multiple entities with varied content, when a semantic query close to one entity is issued, then that entity ranks first in the response.
2. Given a `type` filter, when issued, then only entities of that type appear in results.
3. Given an empty `q`, when issued, then a 400 is returned.
4. Given a query, when results are returned, then each result includes a similarity score.

---

## L2-008: Commitment Attributes
**Traces to:** L1-006

Commitment entities shall store the following keys in `Attributes` JSONB: `cadence` (string: `daily`, `weekly`, etc.), `target` (number), `unit` (string: `min`, `km`, `words`, `call`, etc.). The system shall expose `POST /api/commitments` and `GET /api/commitments` as thin wrappers that create/query Entity rows of type `Commitment`.

Streak and "today done" status are not stored on the entity; they are derived from the commitment activity log (L2-023).

**Acceptance Criteria:**
1. Given a commitment payload with `cadence=daily`, `target=30`, `unit=min`, when posted, then the entity is stored with type `Commitment` and the attributes preserved verbatim in `Attributes` JSONB.
2. Given commitments exist, when `GET /api/commitments` is called, then only Commitment-type entities are returned, each enriched with derived `streak` and `todayDone` fields computed from the activity log.

---

## L2-009: Person Attributes
**Traces to:** L1-006

Person entities shall store the following keys in `Attributes` JSONB: `lastSeen` (string, free-form date label as displayed), `touchpoints` (number), `relationship` (string: e.g., `Close friend`, `Family`, `Mentor`, `Reference`). Tags live on the entity-level `Tags` column (L2-001). The system shall expose `POST /api/contacts` and `GET /api/contacts` as thin wrappers over Person-type entities.

**Acceptance Criteria:**
1. Given a person payload with `lastSeen`, `touchpoints`, and `relationship`, when posted, then the Person entity persists with the contact attributes preserved in `Attributes` JSONB.
2. Given contacts exist, when `GET /api/contacts?q=...` is called, then only Person-type entities matching the query are returned.

---

## L2-010: Responsive Layout
**Traces to:** L1-007

The web client shall use a single-column, vertically stacked layout as its base. Layout shall progressively enhance at breakpoints: sm 576px, md 768px, lg 992px, xl 1200px.

**Acceptance Criteria:**
1. Given a viewport width below 576px, when any page is rendered, then content displays in a single column with no horizontal scroll, the bottom tab bar is visible, and the search input on the Search screen is sticky at the top.
2. Given a viewport width >=768px, when the entity list is rendered, then it displays in a multi-column grid where appropriate.
3. Given a viewport width >=1200px, when any primary screen is rendered, then a side rail (primary navigation, capture button) is visible on the left and a context pane is visible on the right.
4. Given any viewport size, when interactive elements (buttons, links) are rendered, then they have a minimum hit target of 44x44 CSS pixels.

---

## L2-011: Capture Screen
**Traces to:** L1-002, L1-007

The web client shall provide a single capture sheet with a single multi-line text input, a row of type chips (`auto` plus one chip per entity type), a "Looks related to" section listing suggested existing entities matched by the text, and a Save button. The sheet shall be reachable in one tap from anywhere in the app via a global Capture affordance.

When `auto` is selected, the system shall infer the entity type from the input (see L2-024). Saving shall create the entity with the resolved type and store the full input as `Body`; the first sentence (or first 80 characters, whichever is shorter) shall serve as `Title`.

**Acceptance Criteria:**
1. Given any screen in the app, when the user taps the global Capture affordance, then they arrive at the capture sheet with the text input auto-focused.
2. Given the capture sheet is open with text typed and the inferred type displayed, when the user taps Save, then an entity is created and the user is returned to the prior screen with a confirmation toast.
3. Given a viewport width below 576px, when the capture sheet is open, then the on-screen keyboard does not obscure the Save button.
4. Given the capture text matches the title or a tag of an existing entity, when displayed, then up to three suggested entities appear in the "Looks related to" row.

---

## L2-012: Search Screen
**Traces to:** L1-004, L1-005, L1-007

The web client shall provide a search screen with a single text input and a mode toggle: `structured` (substring match against indexed columns) or `semantic` (pgvector cosine similarity via `/api/search`). The user selects one mode at a time; results are not merged across modes.

**Acceptance Criteria:**
1. Given the search screen is rendered, when the user toggles between `structured` and `semantic` modes, then the placeholder text and the request endpoint change accordingly.
2. Given a query is submitted in `semantic` mode, when results return, then a section labeled "Closest in meaning" lists ranked entities.
3. Given a query is submitted in `structured` mode, when results return, then a section labeled "Direct matches" lists entities with title/body/tag substring hits.
4. Given a viewport width below 576px, when the search screen is rendered, then the search input is sticky at the top of the viewport.

---

## L2-013: Authentication
**Status:** Removed.

BrainQ is a single-user local application (L1-008). No sign-in, JWT, or user-identity scoping is required. If a multi-user model becomes necessary, this section will be reintroduced with new acceptance criteria.

---

## L2-014: Password Storage
**Status:** Removed.

See L2-013. Without authentication there are no passwords to store.

---

## L2-015: Input Validation
**Traces to:** L1-009

Every API endpoint shall validate request payloads against an explicit schema. Unknown fields shall be rejected. String inputs shall have enforced maximum lengths (Title <=200, Body <=100000). Output shall be JSON-encoded such that injected scripts cannot execute when rendered by the client.

**Acceptance Criteria:**
1. Given a payload with a Title of 5000 characters, when posted, then a 400 response identifies the field length violation.
2. Given a payload with an unknown field `__proto__`, when posted, then a 400 response is returned.
3. Given an entity body containing `<script>alert(1)</script>`, when fetched and rendered by the client, then no script executes.

---

## L2-016: Transport Security
**Traces to:** L1-009

In any non-development environment, the API shall serve all traffic over HTTPS and shall set HSTS, `X-Content-Type-Options: nosniff`, and a restrictive `Content-Security-Policy` on all responses. Development environments may serve over HTTP on localhost.

**Acceptance Criteria:**
1. Given a non-development deployment, when an HTTP request is made, then it is redirected to HTTPS or rejected.
2. Given a non-development response, when headers are inspected, then `Strict-Transport-Security`, `X-Content-Type-Options`, and `Content-Security-Policy` are present.

---

## L2-017: Rate Limiting
**Traces to:** L1-009, L1-010

The API shall apply rate limiting on write endpoints (POST/PUT/DELETE) at no more than 60 requests per minute per client.

**Acceptance Criteria:**
1. Given 61 write requests within a minute from one client, when the 61st is sent, then a 429 response is returned with a `Retry-After` header.

---

## L2-018: Performance Targets
**Traces to:** L1-010

The system shall meet, on a database with 50,000 entities and 200,000 edges:
- p95 < 200ms for `GET /api/entities/{id}`
- p95 < 500ms for `GET /api/entities` (structured query)
- p95 < 800ms for `GET /api/search` (semantic)
- p95 < 300ms for `POST /api/entities` (excluding embedding when computed in background)

**Acceptance Criteria:**
1. Given a seeded database of the specified scale, when a load test issues each endpoint at 10 RPS for 60 seconds, then p95 latency is within the stated thresholds.
2. Given an entity-by-id query, when measured under load, then no N+1 query patterns appear in EF Core's logs.

---

## L2-019: Health & Logging
**Traces to:** L1-011

The API shall expose `GET /health` returning 200 when the database is reachable and 503 otherwise. The API shall emit structured logs (JSON) for every request including `traceId`, `method`, `path`, `status`, and `durationMs`.

**Acceptance Criteria:**
1. Given the database is reachable, when `GET /health` is called, then 200 is returned with a body listing each dependency's status.
2. Given the database is unreachable, when `GET /health` is called, then 503 is returned.
3. Given an API request completes, when logs are inspected, then a JSON entry exists with the listed fields.

---

## L2-020: Architectural Boundaries
**Traces to:** L1-012

The codebase shall consist of: one ASP.NET Core API project, one EF Core data project (or folder), one web client project, and a tests project. No additional services, message brokers, caches, or background worker hosts shall be introduced. Any deviation requires a new L2 requirement justifying it.

**Acceptance Criteria:**
1. Given the solution file, when inspected, then it contains no more than four projects (API, Data, Web, Tests).
2. Given the deployment configuration, when inspected, then it provisions only a database and the API+Web hosts.

---

## L2-021: Acceptance Test Traceability
**Traces to:** L1-012

Every acceptance test shall include a header comment identifying the L2 requirement(s) it covers using the format `Traces to: L2-XXX[, L2-YYY]`.

**Acceptance Criteria:**
1. Given an acceptance test file, when inspected, then a header comment names at least one L2 id.
2. Given the full test suite, when traceability is generated, then every L2 with a `must`/`shall` clause has at least one test referencing it.

## L2-022: Today Screen
**Traces to:** L1-013

The web client shall provide a Today screen as the default landing surface containing, in order: a date label, a greeting line, a tap-to-capture prompt, a Commitments grid showing every Commitment entity with a progress ring and streak label, an "On your mind" nudges list (soft prompts derived from graph state — overdue people, missed daily commitments, upcoming birthdays), and a "Recently touched" entity list.

**Acceptance Criteria:**
1. Given the app loads with no route, when the Today screen renders, then the date label, greeting, capture prompt, Commitments grid, and "Recently touched" list are all visible.
2. Given a Person entity is tagged `overdue` or has `lastSeen` older than a configured threshold, when the Today screen renders, then a nudge entry referencing that person appears in "On your mind".
3. Given a daily Commitment has not been logged for today, when the Today screen renders, then a nudge entry referencing that commitment appears in "On your mind".
4. Given the user taps the capture prompt, when invoked, then the Capture sheet (L2-011) opens with the text input focused.

---

## L2-023: Commitment Activity Log
**Traces to:** L1-006, L1-013

The system shall persist a `CommitmentActivity` table with columns: `Id` (UUID), `CommitmentEntityId` (UUID, FK to Entity), `DateUtc` (date), `Value` (number, default 1), with a unique index on (`CommitmentEntityId`, `DateUtc`). The system shall expose `POST /api/commitments/{id}/log` to record a completion for a given date and `GET /api/commitments/{id}/activity?weeks=` to return the activity matrix.

The Detail screen for a Commitment shall render an activity heatmap of the last 18 weeks (7 days per column) and a streak count derived from consecutive cadence-eligible days with at least one log entry up to today.

**Acceptance Criteria:**
1. Given a Commitment exists, when `POST /api/commitments/{id}/log` is called for today, then a row is inserted (or upserted) and the response includes the recomputed `streak` and `todayDone=true`.
2. Given 23 consecutive days of log entries for a daily Commitment, when its detail is fetched, then `streak=23` is returned.
3. Given a Commitment with sparse log entries, when its detail screen renders, then the heatmap displays cells shaded in five intensity bands proportional to `Value`, with empty days shown at the lowest band.

---

## L2-024: Capture Auto-Classification
**Traces to:** L1-002

The Capture sheet's `auto` mode shall classify the entity type from the input text using a deterministic heuristic: idea cues (`idea`, `what if`, `maybe i could`, `possibility`) → Idea; commitment cues (`every day`, `daily`, `each week`, `commit`, `goal of`) → Commitment; person cues (`met`, `coffee with`, `called`, `emailed`, `birthday`, or two consecutive Title-Case words) → Person; project cues (`project`, `ship`, `deadline`, `milestone`) → Project; otherwise Note. The detected type shall update live as the user types and shall be visible above the type chip row.

**Acceptance Criteria:**
1. Given the user types "had coffee with Marian Calder", when the classifier runs, then the detected type is `Person`.
2. Given the user selects a non-`auto` chip, when subsequent typing changes the inferred type, then the detected display does not override the user's explicit selection.
3. Given the input is empty, when the classifier runs, then the detected type is `Note`.

---

## L2-025: Personalization (Tweaks)
**Traces to:** L1-014

The web client shall expose a Tweaks panel with three controls: Theme (`light`, `sepia`, `dark`), Accent (`terracotta`, `ink`, `moss`, `ochre`, `rose`), Density (`cozy`, `compact`). Selections shall apply immediately by setting CSS custom properties and shall persist in `localStorage` across sessions.

**Acceptance Criteria:**
1. Given the user changes the Theme value, when applied, then `document.documentElement.dataset.theme` updates to the selected value with no page reload.
2. Given the user changes the Accent value, when applied, then `--bq-accent`, `--bq-accent-soft`, and `--bq-accent-ink` CSS variables update on `:root`.
3. Given a Tweaks selection has been made, when the page reloads, then the previously chosen values are restored from `localStorage`.

---

## L2-026: Detail Screen and Neighborhood Pane
**Traces to:** L1-003, L1-007

The web client shall provide an entity Detail screen showing: a back affordance, a type glyph and label, the entity title and subtitle, the body text, a type-specific stats card (Commitment streak/target/heatmap; Person last-seen/touchpoints/relationship; Project status/due/progress bar), an outbound "Connections" section listing edge chips, and an inbound "Mentioned by" section listing entities whose edges target this one.

At the xl breakpoint, when an entity is open, the right-side context pane shall render a radial Neighborhood graph (the open entity at center, neighbors arrayed on a circle, edges colored by edge type) plus a list of those neighbors with directional indicators.

**Acceptance Criteria:**
1. Given an entity has both outbound and inbound edges, when its Detail screen is rendered, then both "Connections" and "Mentioned by" sections appear with the correct entries.
2. Given an entity is open at a viewport width >=1200px, when the context pane renders, then a radial SVG graph centered on the open entity displays with one node per neighbor, edges colored by edge type.
3. Given a neighbor node is tapped in the graph, when the click is handled, then that neighbor becomes the open entity and the graph re-renders centered on it.

---

## L2-027: People Filter and RecallQ Band
**Traces to:** L1-006

When the Brain screen filter is `Person`, the screen shall display a RecallQ-style header band above the list containing three stats — total people, count overdue, count in close circle — and, if any people are tagged `overdue`, a "Worth a message" section listing those people with last-seen labels and a tap target to open each one.

**Acceptance Criteria:**
1. Given the Brain screen is filtered to `Person` and at least one Person is tagged `overdue`, when the screen renders, then the "Worth a message" section appears with one row per overdue person.
2. Given no Person is tagged `overdue`, when the screen renders, then the "Worth a message" section is omitted.
3. Given the Brain screen filter changes from `Person` to any other type, when the screen re-renders, then the RecallQ band is no longer visible.
